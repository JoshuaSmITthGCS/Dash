# Final Verification Report — ValueSignal Quant Upgrade

Branch `claude/valuesignal-quant-upgrade-1ngvp5`, compared against pre-upgrade baseline
commit `40c32ee` (chore(data): refresh advisor research, 2026-08-06). This is the Phase 11
close-out for the 23-section quant upgrade brief. `docs/CHANGELOG-QUANT-UPGRADE.md` is the
phase-by-phase narrative; this document is the verification and audit snapshot.

## 1. Executive summary

Two live complaints (confidence collapsed to 0.39-0.48 across every published stock, and
visible rank churn between refreshes) traced to one bug: `yahoo_extended()` discarded
successfully-fetched financial statements whenever an unrelated `.info` call failed, so most
stocks scored off ~29% of their fundamental fields. Fixed, with a hard validation gate so it
can't ship silently again. Confidence is now decomposed into components instead of one
opaque number, ETFs and stocks rank in separate pools, technical indicators were added
capped below fundamentals per explicit instruction, and 16 screen presets, a transaction
cost model, portfolio-move explanation, and a Firestore-backed watchlist with price targets
were built. No promotion occurred anywhere in this branch — every new sleeve, screen, and
challenger ships `research_only` / `specification_only` / `prospective_unvalidated`. The
champion scoring model's formulas are unchanged except two additive published fields and one
new 0.06-weighted technical factor.

A second round of live bugs was found and fixed after this branch's first PR (#41) merged:
that merge landed at commit `2692eac`, one commit **before** the actual watchlist/search
bug fixes (`fdc4c6e`) reached the branch, so the fixes never reached `main`. They have since
been rebased onto current `main` and re-pushed; a new PR is needed to land them (see §6).

  governance, walk-forward validation, deflated Sharpe/PBO/IC, point-in-time storage,
  cross-sectional normalization, reconciling attribution, peer groups, and alerts all

## 3. Algorithm architecture changes

- **Enrichment bug fix** (`pipeline/fetch_advisor.py`): decoupled the `.info` and
  statement-frame fetches; `enrich()` now gates on `extended_coverage > 0`. Added
  `enrichment_diagnostics` to the published payload and a hard failure in
  `validate_data.py::enrichment_coverage_errors` if a full sweep enriches zero companies.
- **Confidence redesign** (`pipeline/confidence.py`): publishes
  completeness/freshness/source_reliability/peer_sample/model_agreement components
  alongside the existing scalar. `historical_calibration` is `null` — not invented — until
  the IC harness has eligible periods.
- **Rank-stability diagnostics** (`pipeline/stability_report.py`): confirmed against the real
  committed PIT store that the enrichment bug caused a 10-60x turnover spike. Wired into
  `refresh-advisor.yml` as a non-blocking step so a repeat is visible immediately.
- **ETF/stock separation** (`src/pages/Picks.jsx`, `src/lib/researchScreens.js`): ETFs and
  stocks are scored by different models and are no longer sorted in one mixed pool.
- **Research contract + feature registry** (`pipeline/config/research_contract.json`,
  `pipeline/config/feature_registry.json`, generated by `build_feature_registry.py`):
  centralizes thresholds and classifies all 32 metrics actually referenced by
  `settings.json`, including 12 that were undeclared in the old metric registry.
- **Sleeves** (`pipeline/sleeves/`): value, quality, growth wired through a shared
  fundamentals-family helper; a documented interface for the rest.
- **Technical indicators** (`pipeline/technical_indicators.py`): 4 indicators from 4 distinct
  economic families (MA slope, RSI, Bollinger %B, OBV slope), weighted 0.06 of
  `market_behavior` — capped below fundamentals (0.78) per explicit instruction, not the
  broader "indicator zoo" that was initially proposed and declined on data-snooping grounds.
- **Emerging growth screen** (`src/lib/researchScreens.js`): `rankFastGrowth` renamed to
  `rankBreakoutInProgress` (it detects a move already underway); new `rankEmergingGrowth`
  ships `research_status: "prospective_unvalidated"` with no timing claim.

## 5. Screens, costs, portfolio construction, watchlist

- `pipeline/config/screen_presets.json`: all 16 brief presets registered — 7 wired to a real
  implementation, 9 marked `specification_only` with `implemented_in: null`.
- `pipeline/costs.py`: liquidity-tiered, three-scenario transaction cost model. Not yet wired
  into the IC harness (which still uses a flat rate) — stated in `docs/TRANSACTION-COSTS.md`.
- `shrinkCovarianceMatrix()` added; 1 of 6 brief portfolio-construction methods exists
  (score-weighted) — stated in `docs/PORTFOLIO-CONSTRUCTION.md`.
- `src/lib/portfolioAttribution.js`: exact-reconciling market/idiosyncratic move explanation,
  rendered on `/portfolio` after every refresh.
- `src/lib/useWatchlist.js`, `watchlistPriceTargets.js`: Firestore-backed watchlist with
  volatility-scaled dip-buy and valuation-percentile good-buy price targets, both
  self-documenting via a `derivation` string, wired to the existing alert infrastructure.

## 8. Remaining limitations (honest, not exhaustive elsewhere)

- No live browser or authenticated-Firebase verification was possible from this sandbox — its
  outbound proxy rejects both Yahoo Finance and Firebase entirely. All frontend changes are
  verified by unit test, lint, and build only; the user should exercise the watchlist star,
  mobile nav, and widget-reorder panel in a real browser before relying on them.
- `historical_calibration` confidence component and all promotion gates remain `null` /
  `insufficient_history` by design — there are only 6 scored refreshes and 3 shadow-portfolio
  observations in this repo's history. This is expected, not a bug, and will only resolve
  with time and successfully-run scheduled refreshes.
- Transaction costs are not yet wired into the IC harness (flat rate still used there).
- 9 of 16 screen presets and 5 of 6 portfolio-construction methods from the original brief
  are specification-only — registered and documented, not implemented.
- Widget reordering exists only for the Dashboard/Financial Report screen. Other screens
  (Portfolio, Research, Search, Watchlist) are single fixed-purpose layouts, not built from
  swappable blocks, so "reorder" isn't a coherent action there without a larger rebuild that
  wasn't requested or scoped.
